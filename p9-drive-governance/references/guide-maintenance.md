## One register and stable references

The existing **Change register** is the unified register for major Drive and guide changes. Substantial restructures/consolidations/bulk moves, naming standards, guide-purpose changes and introduction of agent operating rules are major. Ordinary file outputs/uploads and minor wording corrections do not each create a major entry.

1. Search the live register for the same ongoing change using its stable internal key and scope. Extend that entry on retries, corrections and instruction synchronisation rather than allocating another number.
2. Only for a genuinely new major change, read the current register/reservations and select the next unused `CR-YYYY-NNN` for the actual change year. Never hardcode a next number or renumber earlier entries. A continuing change keeps its original reference even when later updated.
3. Preserve date, classification, title, scope, summary, impact, outcome, status and implemented changes. Use actual record/change dates (P9 business time normally Europe/London), not a guessed file timestamp. Mark only verified scope complete.
4. Link permitted subordinate file-detail records through their `batch` value matching the entry's internal `id`; retain the relationship and full-register CSV export. Distinguish created, moved, renamed, staged, returned, copied and trashed outcomes. Historic source locations do not claim the object's current location and still obey the publication boundary.
5. Update applicable folder/rule guidance and **Exceptions & scope**. Record required but unverified Drive/save/publication outcomes as pending. Prepare a concrete patch before seeking any missing publication authority; do not publish merely because a register entry is needed.
